# Plan: CI builds what ships

## Technical context

- **What exists.** `esbuild.mjs` reads `--production` off `process.argv` and sets `minify: production, sourcemap: !production` in `common`, shared by the extension, webview and integration configs. `assertSelfContained("dist/extension.js")` runs at the end of `run()` on whichever mode just built. `vscode:prepublish` is `node esbuild.mjs --production`, which `vsce package` runs; `vsce ls` does not.
- **One named script, so neither CI nor a person has to remember an argument.** `build:production` is `node esbuild.mjs --production`. `vscode:prepublish` keeps its own literal rather than calling the script: `vsce` invokes `vscode:prepublish` directly and an indirection there buys nothing, while the two must not be able to disagree — a test pins them (below).
- **The gate's chain, and the ordering FR-004 asks to settle.** The chain becomes `format:check`, `lint`, `typecheck`, `test`, `build`, `test:integration`, `build:production`, `package` — the production build and the packaging **last**. The reason is `test:integration`: it runs `esbuild.mjs --integration` and reaches the extension through `vscode` and `dist/`, so whichever bundle is on disk is the one it exercises. Leaving the dev bundle there keeps that suite reading the readable build with its sourcemap, which is what a failure in it needs, and the production build then runs afterwards purely to be built and guarded. The alternative — production first, integration against the minified bundle — tests something closer to what ships but makes every integration failure a minified stack trace. That is a real trade and this plan takes the readable side deliberately; FR-004 only requires that the choice be stated, and the pull request states it.
- **`package` after `build:production` is not redundant.** `vsce package` re-runs `vscode:prepublish`, so it builds production a second time. It stays because FR-003 is about the packaging step itself — a `.vsix` that cannot be produced from the tree — and because it is what the release workflow actually runs. The second build costs under a second (measured: 63 ms and 72 ms for the two bundles).
- **Pinning the two production entry points.** A test asserts that `package.json`'s `build:production` and `vscode:prepublish` both run `esbuild.mjs --production`. Without it, someone can change one and leave CI checking a mode nothing publishes — the same class of gap this ticket closes. `test/ci/manifest-couplings.test.ts` already holds `package.json` ↔ `src/` identifier couplings, so the assertion belongs beside it or in its own `test/ci/` file.
- **Proving FR-002 rather than asserting it.** The deliberate break has to trip the guard **only** under minification, or it proves nothing new. `assertSelfContained` matches `["'`]\./…["'`]` in the output; a string literal that esbuild's minifier produces or preserves differently from the dev build is the lever. The task records what was broken and the resulting failure; if no break can be constructed that trips production and not dev, say so in the pull request rather than quietly skipping the criterion — that is a finding about the guard, not a reason to tick the box.
- **The `.vsix` is built and discarded.** Nothing uploads. The gate's working directory is thrown away with the runner, and `.gitignore` already covers `*.vsix`; confirm it does rather than assume.
- **Cost, which is the one thing to measure rather than reason about.** Two extra steps in an existing job: a production build (~150 ms for both bundles) and `vsce package` (seconds). Billed minutes round up per job, so this may or may not cross a boundary — the task reads the actual job duration before and after and the pull request quotes it. That number matters: a step added to a per-push job is spend to justify, not assume.

## Surfaces touched

- `package.json` — a `build:production` script. `vscode:prepublish` unchanged.
- `.github/workflows/build-check.yml` — the `run:` chain gains `npm run build:production` and `npm run package`, in that order, after `test:integration`. The `build` job keeps its name, so the required `build / ci` check reports unchanged and no branch ruleset edit is owed. This is this repo's own stub input, which is where a per-repo gate chain belongs; the reusable workflow it calls is not touched.
- `test/ci/` — a test pinning `build:production` and `vscode:prepublish` to `esbuild.mjs --production`. New behaviour ships with a test.
- `esbuild.mjs` — no change expected. If the deliberate break in FR-002 shows the guard cannot see a minified-only leftover, that is a finding about the guard: report it in the pull request and file it rather than widening the regex in this ticket.
- `.gitignore` — confirm `*.vsix` is covered so a local gate run leaves nothing behind; add it if not.
- `.vscodeignore` — confirm no entry is owed. Nothing new lands in the packaged set; `test/ci/package-contents.test.ts` is the check that proves it, and it already runs in the gate.
- `docs/testing.md` — the gate's chain and what each step is for, including that the last two build and package the mode that ships, and which build `test:integration` runs against.
- `docs/releasing.md` — says the production build and the packaging are already green before the release pull request merges, so the release job is no longer the first place they run.
- `CLAUDE.md` — the Commands block gains `build:production`; the Build gate line lists the new chain; invariant 2 says the guard now runs on the minified bundle in CI. Keep the file under its 8500-byte budget, which its own gate enforces.
- cost — two steps added to an existing per-push job, measured from the job rather than estimated, and quoted in the pull request. No new job, trigger, cron or scheduled function.
- `docs/adr/` — an ADR is plausible here and the build decides: FR-004's ordering choice (integration against the dev bundle, production built after) is a decision with a stated trade-off, which is what `docs/adr/` is for. Write one if the choice survives review; say so either way in the pull request.
- none else — no reusable workflow body in [chrisgriffin/workflows](https://github.com/chrisgriffin/workflows) is touched, no required check renamed, and the published surface is unchanged: `contributes`, the commands and the schema are untouched, and the `.vsix` contents are held by the existing packaged-contents test.
